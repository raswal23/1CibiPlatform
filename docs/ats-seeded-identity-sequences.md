# Seeded Identity Sequences: The "Error Saving Entity" on Add Role

**Branch:** `feature/CIBI-Blue-Extraction`
**Date:** 2026-09-14
**Scope:** ATS Role Management, Module Management, ATS database seeding

## The symptom

Adding a role in Role Management failed with the generic **"error saving entity"** popup. The same fault existed in Module Management, where it was masked — see "Why modules looked fine" below.

Nothing was wrong with the role being added: the name was unique, the validator passed, and the request reached the database. The insert itself died.

## What it does

Advances the PostgreSQL identity sequences behind `ats.RoleDetails."RoleId"` and
`ats.ModuleDetails."ModuleId"` past the rows the seed inserts with explicit ids, so the
first role or module an admin creates gets a free id instead of colliding with a seeded one.

The sync runs on every application start, at the end of `SeedAsync` — not only when the
seed inserted something. Databases seeded before this existed are already wrong, and they
heal on the next start without anyone running a manual script.

## Root cause

Both tables are declared `generated by default as identity`:

```csharp
builder.Property(x => x.RoleId).IsRequired().ValueGeneratedOnAdd();
```

`ATSInitialData` seeds them with **explicit** ids — `RoleId = 1..4` (Platform Manager,
Client Admin, Service Delivery, User), and the `AtsModuleIds` constants for modules.

**An explicit id does not advance the sequence.** `generated by default` means "use the
sequence when no value is supplied" — supply one and the sequence is untouched. So after
seeding, the table held ids 1–4 while the sequence still pointed at 1:

```
 last_value | is_called
------------+-----------
          1 | f
```

The next insert without an explicit id therefore drew `RoleId = 1`, which was already
taken by Platform Manager:

```
ERROR:  duplicate key value violates unique constraint "PK_RoleDetails"
DETAIL:  Key ("RoleId")=(1) already exists.
```

EF surfaces `Npgsql.PostgresException 23505` as a `DbUpdateException`, which reaches the
frontend as the generic **"error saving entity"** message. The popup never named the real
problem, which is why the fault looked like a validation or mapping issue.

Every add attempt failed identically and forever: a failed insert rolls back, so the
sequence never advanced on its own. The table could not grow past its seeded rows.

## Why modules looked fine

`ModuleDetails` had the same defect but a narrower blast radius. The
`20260808061153_SeedATSSuperAdminAccess` migration inserts modules 1–10 and **already ran
this exact `setval`** afterwards, so it left the sequence correct at 10.

`ATSInitialData` then seeds modules 11–15 (Client Assigning, AI Assistant, Bulk Uploads,
Ticketing Status, Audit Trail) with explicit ids and never re-syncs. The sequence stayed
at 10 while the table reached 15 — so the first five module adds would have failed, then
the sixth would have started working. A partial, confusing failure rather than a total one.

Confirmed on the dev database before the fix:

```
LAGGING: ats.RoleDetails(RoleId)     seq max=4  last=1
LAGGING: ats.ModuleDetails(ModuleId) seq max=15 last=10
```

No other table in any schema was affected — those two are the only ones seeded with
explicit ids.

## The fix

`BackendAPI/Modules/ATS/Data/Extensions/ATSDatabaseExtensions.cs` gained
`SyncIdentitySequencesAsync`, mirroring `AuthDatabaseExtensions.SyncIdentitySequences`,
which solved this same problem for the Auth module first. ATS simply never got the
equivalent.

```csharp
SELECT setval(
    pg_get_serial_sequence('ats."RoleDetails"', 'RoleId'),
    GREATEST((SELECT MAX("RoleId") FROM ats."RoleDetails"), 1),
    TRUE);
```

- `pg_get_serial_sequence` resolves identity-column sequences, not just legacy `serial`
  ones — verified against this schema.
- `GREATEST(..., 1)` guards an empty table, where `MAX` is `NULL` and `setval` would fail.
- `TRUE` marks the value as already used, so the next id is `MAX + 1` rather than `MAX`.

It is idempotent — re-running it on a correct sequence sets it to the value it already
holds — which is what makes it safe to run on every start.

### Call ordering

The sync is the **last** step of `SeedAsync`, after
`BackfillModuleGrantedWithNewOrderAsync`. That backfill inserts `ModuleDetails` rows with
explicit ids too, so syncing before it would strand the sequence again on any start where
the backfill adds a module.

### Existing databases

The dev database was repaired directly with the same two `setval` statements. Any other
environment seeded before this change heals on its next application start.

## Tests

`RoleManagementServiceIntegrationTests` — region **Seeded Identity Sequences**:

| Test | Asserts |
|---|---|
| `AddRoleAsync_ShouldPersistRole_WhenSeededRolesHoldExplicitIds` | New role gets `RoleId > 4`; the four seeded rows survive |
| `AddModuleAsync_ShouldPersistModule_WhenSeededModulesHoldExplicitIds` | New module gets `ModuleId > 15` |

Both seed rows with explicit ids through raw SQL and then call the production
`SyncIdentitySequencesAsync`, so they exercise the real fix rather than a copy of it.
`SyncIdentitySequencesAsync` is `public` for exactly this reason.

Both were confirmed to **fail without the fix**, with the same
`duplicate key value violates unique constraint "PK_RoleDetails"` the user saw, and to
pass with it. Full suite: 1021 passed, 0 failed.

## What not to do

- **Do not seed an identity column with an explicit id without syncing its sequence
  afterwards.** This is the whole bug. If a new seed block assigns ids by hand, add the
  table to `SyncIdentitySequencesAsync` in the same change.
- **Do not rely on the integration tests to catch this class of bug by accident.**
  `BaseIntegrationTest.InitializeAsync` truncates with `RESTART IDENTITY`, which leaves
  every sequence agreeing with its (empty) table. A test must recreate the seeded shape
  deliberately, as the two above do.
- **Do not move the sync earlier in `SeedAsync`.** Anything that inserts explicit ids
  after it re-strands the sequence.
- **Do not "fix" this by giving new roles an explicit id in the repository.** That
  spreads the defect instead of removing it, and reintroduces a race between concurrent
  admins.
- **Do not drop the `GREATEST(..., 1)` guard.** On a fresh, empty table `MAX` is `NULL`
  and `setval` raises rather than no-opping.
- **Do not assume "error saving entity" is a mapping or validation problem.** It is the
  frontend's fallback for any `DbUpdateException`; read the Postgres `SQLSTATE` before
  diagnosing. `23505` is a unique/PK violation.

## Verify

1. Start the API against a database seeded by `ATSInitialData`.
2. Role Management → **Add role** with a unique name → saves, no popup.
3. Check the new row's `RoleId` is above 4.
4. Module Management → **Add module** → saves; `ModuleId` above 15.
5. Restart the API and repeat — the sync is idempotent, so ids keep climbing.
6. To confirm no sequence lags anywhere, run the audit query over all schemas comparing
   each sequence's `last_value` against `MAX` of the column it backs.
